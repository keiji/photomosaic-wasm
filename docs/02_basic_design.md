## 1. 画面一覧と画面遷移

### 1.1 共通の画面構成方針

Web・Android ともに UI の構造は同一とし、画面の大幅な差分を作らない。
入力手段の差異のみを吸収する。

| 項目 | Web | Android |
|---|---|---|
| メイン画像の設定 | ファイル選択 + ドラッグ & ドロップ | ボタン → メディアピッカー(単一選択) |
| 構成画像の設定 | 複数ファイルのドラッグ & ドロップ + ファイル選択 | ボタン → メディアピッカー(複数選択) |
| 保存 | ブラウザダウンロード | メディア保存 + 共有 |

### 1.2 画面一覧

| 画面ID | 画面名 | 説明 |
|---|---|---|
| S1 | 開始画面 | メイン画像の設定と構成画像の追加を行う起点画面 |
| S2 | 編集画面 | メイン画像プレビュー、ブロックサイズ調整、進捗表示、保存を行う主画面 |
| S3 | 進捗確認(領域) | 独立画面ではなく S2 内の進捗表示領域として実装。ユーザー操作で表示/非表示を切り替えられる |

※ 本アプリは状態遷移が少ないため、Web では SPA(単一ページ + 表示状態の切替)、Android では単一 Activity + Compose の状態切替とする。

### 1.3 画面遷移図

```
[S1 開始画面]
   │  メイン画像を設定
   ▼
[S2 編集画面] ─────────────────────────────────────┐
   │                                                │
   │  (S1 で構成画像を設定済みなら、到着時点で        │
   │   フォトモザイク生成が自動的に開始される)        │
   │                                                │
   │  ┌─ S2 内で可能な操作 ────────────────────┐    │
   │  │ ・ブロックサイズの変更(再生成)          │    │
   │  │ ・構成画像の追加/削除(追加分のみ再マッチ)│   │
   │  │ ・進捗表示領域の開閉(表示/非表示)        │    │
   │  │ ・進捗バーの確認                        │    │
   │  │ ・保存                                  │    │
   │  └────────────────────────────────────────┘    │
   │                                                │
   │  「リセット」                                   │
   ▼                                                │
[S1 開始画面] ◀────────────────────────────────────┘
```

### 1.4 状態遷移モデル

アプリ内部の状態は次の 4 状態で管理する。UI はこの状態に応じて表示を切り替える。

| 状態 | 説明 | 画面上の表示 |
|---|---|---|
| `EMPTY` | 何も設定されていない | S1 の入力 UI のみ |
| `TILES_READY` | 構成画像のみ設定済み(メイン画像未設定) | S1。構成画像サムネイル一覧 + 「メイン画像を選択してください」案内 |
| `MAIN_READY` | メイン画像のみ設定済み | S2。メイン画像プレビュー + グリッド線 + ブロックサイズ UI。「構成画像を追加してください」案内 |
| `GENERATING` | タイルがあり生成処理中 | S2。進捗バーとフェーズ表示。部分結果が順次プレビューへ反映 |
| `DONE` | 生成完了 | S2。フォトモザイク表示 + 保存ボタン有効 |

補足:
- `EMPTY` で構成画像を追加すると `TILES_READY` になる。`TILES_READY` でメイン画像を設定すると即座に `GENERATING` となる(生成の自動開始)。
- `TILES_READY` で構成画像をすべて削除すると `EMPTY` へ戻る。
- `GENERATING` 中でもタイル追加・ブロックサイズ変更の操作は受け付ける(内部では再マッチ要求としてキューイングする)。
- タイルが 0 枚に戻った場合は `MAIN_READY` へ戻る(フォトモザイク表示は解除し、メイン画像 + グリッド表示に戻る)。

| 要素 | Web | Android |
|---|---|---|
| プレビュー | `<canvas>`。クリック/ドロップでメイン画像を変更する(基本設計書 3.3 の「メイン画像の設定・変更」) | Compose `Canvas` + `ImageBitmap` |
| ブロックサイズ | `<input type="range">` 8〜128 px。右側に現在値(px)を表示。ドラッグ中は再計算せず、確定(マウスを離した)時に再生成する | `Slider` 8〜128 px(300ms デバウンス) |
| メイン画像に適合させる | `<input type="range">` 0〜0.8。右側に現在値(0.00〜0.80)を表示。メイン画像を合成結果へ重ねる不透明度。ドラッグ中は再計算せず、確定(マウスを離した)時に再生成する | `Slider` 0〜0.8 |
| 色補正の強さ | `<input type="range">` 0〜1.0。右側に現在値(0.00〜1.00)を表示。タイルのトーンをブロック平均色へ寄せる強さ(詳細設計書 4.6 の α)。ドラッグ中は再計算せず、確定(マウスを離した)時に再生成する | `Slider` 0〜1.0 |
| 重複とみなす色の近さ | `<input type="range">` 0.5〜8.0。右側に現在値(0.5〜8.0)を表示。似たタイルを「重複グループ」として同一視する代表色の距離(詳細設計書 4.4 の duplicate_de)。ドラッグ中は再計算せず、確定(マウスを離した)時に再生成する | `Slider` 0.5〜8.0 |
| 同じ写真を繰り返さない | `<input type="checkbox">` 既定 ON。似た特徴量のタイルグループを作品内で最大 1 回だけ使う(詳細設計書 4.4 の no_reuse)。「似た特徴量の画像は同じグループとしてまとめ、画像枚数と使用できるグループ数は一致しない」旨の注釈を表示する。タイル不足時は余ったブロックを背景のまま残す。変更時にフル再生成する | 未実装(コア既定 ON) |
| 進捗バー | 横方向のプログレスバー + 「割当済/全体ブロック数」ラベル | `LinearProgressIndicator` + 同ラベル |
| フェーズ表示 | 現在のフェーズ名を短文で表示 | 同左 |
| 進捗表示の開閉 | 進捗表示領域の開閉ボタン(既定: 表示)。非表示中も処理とプレビュー更新は継続 | 同左 |
| 構成画像一覧 | サムネイルグリッド + 個別削除。初期表示は最初に読み込んだ 20 枚程度を限度とし、一覧下の「すべての画像を表示」で読み込み済みの全枚数を表示する。読み込み中は一覧上部に「読み込み中 x枚中y枚」(処理済み/受け付け数)を表示する | 同左(`LazyVerticalGrid` 等) |
| 保存 | 保存形式を選択してダウンロード(PNG 既定 / JPEG 品質 92。M8 で選択 UI を追加) | MediaStore 保存後、共有シートを任意で起動 |
| 戻る/リセット | 開始画面へ戻る(全状態クリア) | 同左 |

### 2.3 進捗表示仕様

進捗表示は 2 層構成とする。

1. **フェーズ表示**: 現在のフェーズ名を表示する。
   フェーズは「読み込み → 解析(メイン) → 解析(タイル) → マッチング → 合成 → 保存」。
2. **横方向進捗バー**: メイン画像の分割後に確定する全体ブロック数に対する、割り当て済み(マッチ済み)ブロック数の割合を帯で示す。
   - ラベル例: `12,480 / 30,000 ブロック (41%)`
   - マッチング完了後の合成フェーズではバーは 100% を維持し、フェーズ表示が「合成中…」に変わる。

進捗表示領域はユーザー操作で表示/非表示を切り替えられる。

| 項目 | 仕様 |
|---|---|
| 切替操作 | 進捗表示領域ヘッダの開閉ボタン(`[非表示 ▲]` / `[表示 ▼]`) |
| 既定 | 表示 |
| 非表示中の動作 | 生成処理・進捗イベント受信・プレビューへの部分描画はすべて継続する。完了時は保存ボタンの有効化で完了を知らせる |
| 切替状態の保持 | ユーザー設定として保持する(Web: localStorage / Android: SharedPreferences) |
| アクセシビリティ | 開閉ボタンには開閉状態が読み上げられる属性を付与する(Web: `aria-expanded` / Android: `stateDescription`) |

進捗イベントそのものの設計(フェーズ定義・コールバック形式・発火間隔)は [詳細設計書の進捗コールバック設計](./03_detailed_design.md#7-進捗コールバック設計) を参照。

## 3. 処理の流れ(フォトモザイク合成の詳細を除く)

### 3.1 全体シーケンス

```
ユーザー        UI層(Web/Android)  ホスト層(Web / JSサンドボックス)   OS
  │                │                          │                     │
  │ メイン画像設定   │                          │                     │
  ├───────────────►│ ファイル取得・検証         │                     │
  │                │ デコード+縮小 ────────────►│ setMainImage()      │
  │                │                          │ グリッド計算・        │
  │                │◄───────── 進捗イベント ───│ ブロック特徴量算出    │
  │                │ 全体ブロック数を表示       │                     │
  │                │                          │                     │
  │ 構成画像追加    │                          │                     │
  ├───────────────►│ デコード+縮小 ────────────►│ addTile() × N       │
  │                │ run() ───────────────────►│                     │
  │                │◄───────── 進捗イベント ───│ 解析→マッチ→合成     │
  │                │ 部分結果を逐次プレビュー反映 │                     │
  │                │                          │                     │
  │ 保存           │ エクスポート要求 ──────────►│ export()            │
  │                │◄───────── RGBA/エンコード ─│                     │
  │                │ ダウンロード / MediaStore  │                     │
  ▼                ▼                          ▼                     ▼
```

### 3.2 処理ステップ定義(UI 層の責務)

| # | ステップ | 内容 | 実行者 |
|---|---|---|---|
| 1 | ファイル受付 | ドロップ/ピッカーで得たファイルの形式・サイズ検証 | UI 層 |
| 2 | デコード | 画像ファイルを RGBA ピクセルバッファへ展開。EXIF 回転を反映 | ホスト側(Web: ページの JS / Android: Kotlin) |
| 3 | 前処理 | 長辺が上限(4096px)を超える場合は縮小。解析・合成・出力はすべて正規化後の解像度で行う | ホスト側(Web: ページの JS / Android: Kotlin) |
| 4 | コア受渡し | RGBA バッファと幅・高さをコアへ渡す(コピー or 転送) | ホスト層 |
| 5 | コア処理 | グリッド計算 → 特徴量 → マッチング → 合成。進捗イベントを随時通知 | コア |
| 6 | 進捗反映 | 進捗イベントを受けてバー・ラベル・プレビューを更新 | UI 層 |
| 7 | 部分描画 | マッチ済み行バッチ単位でプレビューへ逐次反映 | UI 層 |
| 8 | エクスポート | コアから完成 RGBA を取得し、保存形式へエンコード | ホスト側(Web: ページの JS / Android: Kotlin) |
| 9 | 保存 | Web: ダウンロード。Android: MediaStore + 共有 | UI 層(OS 機能) |

- 画像デコード・エンコードはコアを経由しない(ホスト側の標準機能を利用)。コアは「RGBA ピクセル配列」のみを入出力とする。
- この分離により、コアのポータビリティ(WASM)を保つ。
- ホスト層とは WASM コアを動かす実行環境を指す。Web はページ自身の JS 環境、Android は JavaScript エンジン サンドボックス(androidx.javascriptengine: `JavaScriptSandbox` / `JavaScriptIsolate`)であり、両者で同一の .wasm を実行する。Android のホストとの双方向通信は MessagePort API を使用し、JNI によるネイティブコードの実行は行わない(セキュリティ方針)。

### 3.3 操作別の再処理ルール

| 操作 | 再処理の範囲 | 備考 |
|---|---|---|
| メイン画像の設定・変更 | 全処理をリセットしてやり直し | タイルプールは維持(タイルはメイン画像に依存しない) |
| ブロックサイズ変更 | グリッド再計算 → 全ブロック再マッチ → 再合成 | タイル特徴量はキャッシュ再利用。Web はドラッグ中に再生成せず、スライダー確定時に発火。Android は 300ms デバウンス後に発火 |
| メイン画像ブレンド変更 | 設定更新 → 全ブロック再合成(フル再生成) | スライダーはドラッグ中は再計算せず、確定(マウスを離した)時に発火 |
| 色補正強度変更 | 設定更新 → 全ブロック再合成(フル再生成) | 同上 |
| 重複制御変更 | 設定更新 → 全ブロック再マッチ → 再合成(重複グループの再構築) | 同上 |
| タイル追加 | 追加タイルの解析 → 未確定ブロックの再マッチ → 再合成 | 既にマッチ済みのブロックは、追加タイルでより良い候補があれば差し替え(詳細設計書参照) |
| タイル削除 | 該当タイルが割り当てられていたブロックのみ再マッチ | |
| リセット | 全状態クリア → S1 へ | |

### 3.4 保存フロー

**Web**
1. コアから完成画像の RGBA バッファを受け取る。
2. `OffscreenCanvas` / `<canvas>` に描画し `toBlob()` で PNG(既定)または JPEG(品質 92)を生成する(保存形式は UI で選択。M8)。
3. `<a download>` 経由でダウンロードを開始する。ファイル名は `photomosaic_YYYYMMDD_HHMMSS.png`(JPEG 選択時は `.jpg`)。

**Android**
1. コアから完成画像の RGBA を受け取り、Kotlin 側で Bitmap 化して PNG へエンコードする(エンコードは Kotlin。コアは RGBA のみを返す)。
2. MediaStore の `Pictures/Photomosaic`(または `Downloads`)へ PNG で保存する。
3. 保存完了後に「共有」ボタンを表示し、`ACTION_SEND` + FileProvider で共有シートを起動できる。
4. スコープドストレージにより、保存にストレージ権限は不要とする。

共通の保存仕様:
- 出力画像には入力画像のメタデータ(EXIF の撮影位置・撮影日等)を引き継がない。ピクセルバッファからの再エンコードにより取り除く(プライバシー保証。詳細設計書・テスト設計を参照)。

## 4. 入力検証とエラーハンドリング

| ケース | 挙動 |
|---|---|
| 非対応形式のファイル | 追加を拒否し、理由をメッセージ表示(トースト/インライン) |
| メイン画像が大きい(長辺 4096px 超) | 正規化(長辺 4096px へ縮小)して処理し、出力は正規化後の解像度となることを案内する |
| 極端に小さい画像(短辺がブロックサイズ未満) | ブロックサイズの上限を自動調整して案内 |
| 構成画像 0 枚のまま生成要求 | 生成せず「構成画像を追加してください」を案内(グリッド + 平均色プレビューは可能) |
| メモリ不足 | 処理を中止し、ブロックサイズを大きくする・画像を小さくする旨を案内 |
| 処理中の中断(タブ移動等) | コアのキャンセル API で処理を停止し、状態を破棄しない |

## 5. 非機能要件

| 項目 | 要件 |
|---|---|
| オフライン | Web は Service Worker で静的アセットをキャッシュし、2 回目以降は完全オフライン。Android は `INTERNET` 権限なし |
| レスポンシブ | Web はスマートフォン縦持ちを第一対象にレイアウト(ドロップ領域はタップ入力にフォールバック) |
| 応答性 | UI スレッドをブロックしない。Web は WASM 内の進捗チェックで UI へ譲り、Android は JavaScript エンジン サンドボックス(別プロセス)で処理が進むためアプリの UI スレッドを塞がない |
| アクセシビリティ | 進捗バーには `role="progressbar"`/`progressBarAccessibility` 相当の属性を付与し、ラベルで数値を読み上げ可能にする |
| 国際化 | 日本語 UI のみを初期スコープとする(文言はリソース分離しておく) |

## 6. Web と Android の入出力差異まとめ

| 差異点 | Web | Android |
|---|---|---|
| ファイル入力 | `File` オブジェクト → `createImageBitmap` | `Uri` → Kotlin でデコード(EXIF 反映・縮小)し、RGBA をサンドボックスへ渡す |
| ドロップ受付 | あり(デスクトップ)/なし(モバイルはタップ) | なし(ピッカーのみ) |
| 複数選択上限 | 実用上無制限(メモリガードで制御) | Photo Picker の上限(`MAX_ITEMS`、概ね 100 程度を想定し分割追加を案内) |
| 保存 | ダウンロード | MediaStore 保存 + 共有 |
| バックキー | リセット確認ダイアログ | 戻るジェスチャーでリセット確認 |
