# ハンドオフ資料 5: 性能の計測設計

| 項目 | 内容 |
|---|---|
| 性格 | フォトモザイク処理の各部でどの程度の時間がかかるかを、常時・自動で計測可能にするための設計 |
| 対象 | コア・Web・Android の実装者、性能検証担当 |

## 1. 目的

1. ボトルネックの特定: マッチング・合成・色変換など、どの部品が時間を使っているかを必ず数値で語れるようにする。
2. 調整の拠り所: 閾値(重み・バッチサイズ・サムネイル解像度)を変えるたびに効果を実測する。
3. リグレッション検知: 改修のたびに性能が落ちていないかを CI で確認する。
4. 機種差の把握: Web(デスクトップ/モバイルブラウザ)と Android(実機)の差を実測データで比較する。

## 2. 計測の基本設計

- 計測は **コア内部に組み込み** とする。外側からラップする方式(JS 側のタイマー)は、WASM↔JS の往復コストが混ざって正確に計れないため。
- 計測結果はメトリクス構造体に累積し、`getMetrics()` で JSON として取得する。UI への表示・保存はプラットフォーム側の自由とする。
- 計測自体のオーバーヘッドを無視できないので、タイマー呼び出しはバッチ境界・フェーズ境界のみに限定する(ブロック単位では計らない)。
- 決定性: メトリクスの値はゴールデン画像テストの判定に使わない(環境差で変わるため)。
- Android のサンドボックス(V8 系の JavaScript エンジン)も Web と近い実行環境のため、WASM の実行性能は Web と同程度を期待できる。JIT ウォームアップの影響を避けるため、ベンチは 2 回実行して 2 回目を採用する。

## 3. 計測ポイント(スパン)の一覧

| スパン ID | 区間 | 取る値 |
|---|---|---|
| `p1_grid` | グリッド計算 | 時間 |
| `p1_block_features` | ブロック特徴量算出 | 時間 |
| `p2_tile_analyze` | タイル 1 枚の特徴量算出 | 時間(累計・最大・平均) |
| `p2_index_build` | プールの補助インデックス構築(k-d 木・重複グループ。詳細設計書 4.4/4.5) | 時間(構築時のみ) |
| `p3_match_batch` | 行バッチ 1 回分のマッチング | 時間(累計・最大・平均) |
| `p3_match_total` | マッチング全体 | 時間 |
| `p4_compose_batch` | 行バッチ 1 回分の合成 | 時間(累計) |
| `p4_compose_total` | 合成全体 | 時間 |
| `alloc_wasm_heap` | ヒープ伸長が発生した時点 | 発生回数・要求サイズ |
| `mem_peak` | 主要フェーズ終了時点 | 使用メモリ推定量(WASM ヒープ使用量) |

ホスト側で別途計るもの(コア外):
- `host_decode`(ファイルデコード)、`host_scale`(縮小)、`host_encode`(保存形式へのエンコード)、`host_draw`(プレビュー転写)
- Android のみ: `bridge_out`(Kotlin → サンドボックスのデータ受渡し: named data / MessagePort)、`bridge_in`(完成 RGBA・進捗の受渡し)。バイト列転送コストを監視する
- 計時: Web は `performance.now()`(サブミリ秒解像度)/ Android は Kotlin 側 `System.nanoTime()` を基準に、サンドボックス内のフェーズ時間はメッセージ受信時刻差で計る(サンドボックス環境には `performance` が無い場合があるため)

## 4. メトリクス JSON スキーマ(`getMetrics()` の出力)

```json
{
  "core_version": "0.1.0",
  "started_at": "2026-10-18T10:00:00Z",
  "runs": [
    {
      "run_id": 1,
      "trigger": "initial",
      "phases": {
        "P1_MAIN_ANALYZE": { "ms": 212.4 },
        "P2_TILE_ANALYZE": { "ms": 168.9, "tiles": 300 },
        "P3_MATCH":        { "ms": 812.3, "batches": 16 },
        "P4_COMPOSE":      { "ms": 655.0, "batches": 16 }
      },
      "spans": {
        "p3_match_batch": { "count": 16, "avg_ms": 50.8, "max_ms": 71.2 }
      },
      "memory": {
        "wasm_heap_bytes": 104857600,
        "tiles_bytes": 19660800
      },
      "config": {
        "block_size": 24,
        "w_c": 1.0,
        "w_d": 0.25,
        "alpha": 0.85,
        "main_blend": 0.2,
        "duplicate_de": 2.0,
        "duplicate_detail": 4.0,
        "neighbor_de": 8.0,
        "row_batch": 8
      }
    }
  ]
}
```

- `trigger` は `initial` / `block_size_change` / `tile_added` / `tile_removed` を区別し、再生成の効果を比較できるようにする。
- `config` を一緒に記録することで、「どの閾値のときの数字か」を失くさない。

## 5. 計測用データセット(ベンチの共通条件)

比較可能性を保つため、次の固定データセットを `tools/bench/` に用意する。

| セット | 内容 | 用途 |
|---|---|---|
| S-small | メイン 2MP(1600×1200)+ タイル 50 枚 | 開発時の高速確認 |
| S-mid | メイン 12MP(4000×3000)+ タイル 300 枚 | 性能目標の判定用(標準) |
| S-large | メイン 12MP + タイル 2,000 枚 | k-d 木切り替え・メモリ検証 |
| S-block | メイン 12MP、ブロック 8px(極小)〜128px(極大) | ブロックサイズ別の挙動 |

- タイルは生成スクリプトで作る決定的な合成画像(乱数シード固定)を用い、ライセンス問題を避ける。
- スクリプトは PNG とマニフェスト(JSON)を出力し、全プラットフォームで同一データを使う。

## 6. 計測の実施形態

| 形態 | 内容 |
|---|---|
| 開発中オーバーレイ | Web のデバッグビルドでフェーズ時間・バッチ所要を常時表示 |
| ベンチページ | Web に `/bench` ルートを用意。データセットを選んで実行し、メトリクス JSON を表示・ダウンロード |
| CLI ベンチ | Node 上で同じ .wasm を読み込みバッチ実行。CI 用 |
| Android 実機ベンチ | デバッグメニューからベンチ実行 → メトリクス JSON を共有シートへ出力 |

## 7. 性能目標(再掲)とリグレッション基準

参考目標(ミッドレンジデスクトップ相当、S-mid):

| 項目 | 目標 |
|---|---|
| P1 | 300 ms 以内 |
| P2(300 枚) | 200 ms 以内 |
| P3 | 1,000 ms 以内 |
| P4 | 1,000 ms 以内 |
| 初回合計 | 3,000 ms 以内 |
| ブロックサイズ変更後の再生成 | 1,500 ms 以内 |
| WASM バイナリ | 500 KB 以内 |

リグレッション運用:
- CLI ベンチを CI で夜間実行し、目標超過・前週比 20% 超の悪化を検知したら失敗扱いにする。
- 悪化時はメトリクス JSON を添えて PR で議論する(数字なしでマージしない)。
- Android 実機の絶対目標値は設定しない(端末構成のばらつきが大きいため)。実機計測は同一端末での前回比による変化検知に用い、しきい値による CI 判定は CLI/デスクトップベンチにのみ適用する。

- Android のタイル追加は evaluate フォールバックでは 1 枚ごとに制御要求が発生する。300 枚で約 15.9 秒、2,000 枚で約 105 秒。UI は進捗を表示するが、タイル一括登録 API は A4 のフィードバック候補。
- A4-01 の `addTiles` control 導入後は、エミュレータで 300 枚 181 ms、2,000 枚 717 ms。Pixel 8a では 300 枚 660 ms、2,000 枚 1,885 ms。
- MessagePort の ArrayBuffer は Binder のサイズ上限を超えられない。48 MB の完成 RGBA を 1 メッセージで送ると `IllegalArgumentException: arrayBuffer is too large` になるため、JS → Kotlin も 512 KiB チャンクへ分割する。Pixel 8a の全 25 テストはこの方式で成功した。
- S-mid の P4 はデスクトップ目標 1,000 ms を超えるが、Android 実機の絶対目標値は設定しない(§7)。Pixel 8a の P4 は 2.98 秒で、端末差による差が大きい。
