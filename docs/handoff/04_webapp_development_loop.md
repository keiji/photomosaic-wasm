# ハンドオフ資料 4: Web アプリの開発手順(ループ開発計画)

| 項目 | 内容 |
|---|---|
| 性格 | Web アプリを「いきなり全部作る」のではなく、WASM バイナリと組み合わせて機能拡張を繰り返すためのループ開発計画 |
| 対象 | Web アプリ・コアの実装者 |

## 1. 基本方針

1. **薄く始めて厚くする**: 各マイルストーンで「動くもの」を残し、常時デモ可能な状態を保つ。
2. **コアと UI を一緒に伸ばす**: 各マイルストーンは「コアの関数追加 → バインディング → UI 結線 → 計測 → 調整」の 1 ループで構成する。
3. **計測をループの一部にする**: マイルストーンの完了条件に性能計測の記録を含める([性能計測設計](./05_performance_measurement.md))。
4. **Android を想定して API を固める**: Web で確定した論理 API と .wasm がそのまま Android の JavaScript エンジン ホスト(androidx.javascriptengine)で動くよう、M4 までにインターフェースを凍結する([06_android_implementation_guide.md](./06_android_implementation_guide.md))。

## 2. リポジトリ・開発環境の初期整備

| 項目 | 内容 |
|---|---|
| パッケージ管理 | web/ は npm。コアは Cargo。単一リポジトリで管理 |
| ビルドツール | Vite + TypeScript(`strict` 有効) |
| テスト | Vitest(ロジック)、wasm-bindgen-test(コア結合) |
| 静的検査 | `cargo fmt` / `cargo clippy` / `tsc --noEmit` / ESLint / Prettier |
| CI 最小構成 | 上記検査 + `wasm-pack build` + 単体テスト(プッシュ毎) |
| モック方針 | コア未完成の間は同じ論理 API を持つ TypeScript モック(`core/bridge.ts` の差し替え先)を用意し、UI 開発をブロックしない |

## 3. マイルストーン一覧

| MS | 名称 | でできること(デモ) |
|---|---|---|
| M0 | 土台整備 | 開始画面の見た目・画面遷移が動く(処理はモック) |
| M1 | WASM 骨格 | サンプル関数を WASM 経由で実行し、進捗コールバックが UI に出る |
| M2 | メイン画像解析 | メイン画像設定 → グリッド線プレビュー + 全体ブロック数表示 |
| M3 | タイル取り込み | 構成画像を追加 → 解析 → プール表示(サムネイル・枚数) |
| M4 | 一括生成 | タイルあり状態でフォトモザイク一括生成 → 完成表示 + 保存 |
| M5 | 進捗と部分描画 | 段階的置き換え表示 + 横方向進捗バー + キャンセル |
| M6 | インタラクティブ化 | ブロックサイズスライダーでの即時再生成、タイル追加の差分再マッチ |
| M7 | 性能と強健性 | 計測オーバーレイ、メモリガード、巨大画像対応、オフラインキャッシュ |
| M8 | 仕上げ | 設定(色補正強度・重複制御)、保存形式選択、a11y、仕上げのリファクタ |

## 4. 各マイルストーンの詳細

### M0: 土台整備(コア未使用)

- 目的: 画面遷移・状態管理・ファイル入出力の筋道だけを通す。
- 内容:
  - S1/S2 の UI 骨格、状態遷移モデル(`EMPTY` / `MAIN_READY` / `GENERATING` / `DONE`)実装
  - ファイル検証・デコード・EXIF 反映・縮小(`io/imageLoader.ts`)
  - モックコア: `setMainImage` 等を Promise で返す TS 実装(グリッド計算のみ実装)
  - ダウンロードの動作確認(適当な画像のエクスポート経路)
- 完了条件: メイン画像設定 → グリッド表示 → リセットがモックで一巡する。

### M1: WASM 骨格

- 目的: ビルド〜配信〜呼び出し〜進捗コールバックの経路を本物にする。
- 内容:
  - `core` クレート骨格 + `core-wasm`(wasm-bindgen)のサンプル API(`getVersion` 等)
  - `core/bridge.ts` で WASM ロード・メモリ管理・コールバック登録を実装
  - 進捗イベントの発火テスト(ダミー処理 1 秒、間隔 16ms の仕様遵守)
- 完了条件: CI で `wasm-pack build` が緑。バイナリサイズ記録(基準値作り)。[02_wasm_build_guide.md](./02_wasm_build_guide.md) の検収基準を満たす。

### M2: メイン画像解析

- 目的: 最初の本物のコア処理(P1)を通す。
- 内容:
  - コア: `color.rs`(sRGB→線形→CIELAB)、`grid.rs`(グリッド・ブロック特徴量)
  - Web: プレビューへグリッド線 + 各ブロック平均色のタイル状表示
  - 全体ブロック数の表示(進捗バーの分母が確定)
  - ゴールデン画像テストの整備(固定入力・決定的出力)
- 完了条件: 色変換の単体テストが既知値で合格。プレビューが仕様どおり。

### M3: タイル取り込み

- 目的: P2 を通し、タイルプールの UX を固める。
- 内容:
  - コア: `tile.rs`(サムネイル特徴量・プール管理)
  - Web: ドロップ領域の複数ファイル受付、サムネイル一覧・個別削除
  - メモリガードの初版(タイル合計サイズ監視)
- 完了条件: 300 枚程度の追加で UI が固まらず、特徴量が 1 枚あたり数 ms で計算される。

### M4: 一括生成(初めてのフォトモザイク)

- 目的: P3+P4 の直列実行で完成画像を作る。
- 内容:
  - コア: `match_engine.rs`、`compose.rs`(距離関数・使用ペナルティ・色補正)
  - Web: 生成ボタン → 完成表示 → 保存(PNG ダウンロード)
  - 設定 JSON(`getConfig/setConfig`)の導入
- 完了条件: 代表データセット(性能計測設計参照)で完成画像が生成され、目に見えて破綻しない。ここで論理 API を**凍結**し、Android 側の着手準備を整える。

### M5: 進捗と部分描画

- 目的: UX の目玉である段階的置き換えと進捗バーを実装する。
- 内容:
  - コア: 行バッチ化(既定 8 行)、`onProgress` / `onResult` / `cancel()` の実装
  - Web: 横方向進捗バー(`assigned / total`)、部分結果の逐次転写、キャンセル操作
- 完了条件: 進捗イベント間隔が仕様(16ms)どおり。キャンセルがバッチ境界で効く。

### M6: インタラクティブ化

- 目的: ブロックサイズ変更・タイル追加削除への追随。
- 内容:
  - スライダーのデバウンス(300ms)→ `setBlockSize` → 再生成(P2 スキップ)
  - タイル追加時の差分再マッチ(未確定ブロックのみ)
  - タイル削除時の該当ブロック再マッチ
- 完了条件: スライダーを連続操作しても UI が固まらず、1 秒前後で追従する(実測を記録)。
- 実施結果(2026-10-19):
  - 実装コミット: `db9d3f2`(feat(core,web): implement interactive regeneration and differential rematch)
  - 実測 1(headless Chrome / メイン 1200×900・タイル 24 枚 / ブロック 24→40 を 12 回の連続 input):
    - 連続操作 193ms・rAF 最大遅延 17ms(フレーム落ちなし = UI 固まりなし)
    - 最終 input から再生成完了まで 828ms(デバウンス 300ms を含む)
    - 末尾のブロックサイズ(40px)のみで確定(要求の合流・7.5)
    - タイル追加の差分再マッチ 258ms、タイル削除の差分再マッチ 282ms(エンドツーエンド)
  - 実測 2(WASM release / node / メイン 1600×1200・タイル 50 枚):
    - 初回生成(24px)420ms
    - ブロックサイズ変更後の再生成(P2 スキップ)616ms(詳細設計書 10 章: 目標 1.5 秒)
    - タイル追加の差分再マッチ(差し替え評価)6ms

### M7: 性能と強健性

- 目的: 計測の常時化と境界条件の仕上げ。
- 内容:
  - `metrics.rs` の導入(スパン計測)、デバッグオーバーレイ表示、`getMetrics()` の UI 出力
  - メモリガード・巨大画像ガイド・エラー文言整備
  - Service Worker による完全オフライン化(2 回目以降)
  - k-d 木の実装(タイル 2,000 枚超の切り替え)と効果測定
- 完了条件: 性能目標([詳細設計書 10 章](../03_detailed_design.md#10-性能目標と計測))を満たすことの記録。
- 実施結果(2026-10-19):
  - コア: `metrics.rs`(スパン計測・`getMetrics` JSON。handoff/05 §4 スキーマ準拠)、
    `kdtree.rs`(タイル > 2,000 枚で重み付き近傍上位 32 件に絞り、使用/隣接ペナルティを含む
    完全距離で再評価)、メモリガードのサムネイル長辺自動半減(下限 16 px)、
    開発オーバーレイ(`web/src/ui/metricsOverlay.ts`。本番ビルドでは生成されない)、
    Service Worker(`web/public/sw.js`)による 2 回目以降の完全オフライン化、
    巨大画像(長辺 4,096 px 超)の自動縮小案内
  - 実測: handoff/05 §9 に記録(S-mid の全目標達成: P1 100 / P2 40 / P3 385 / P4 700 /
    初回相当合計 1,185 ms・再生成 1,195 ms)。P4 は 2,578 → 700 ms、P1 は 1,507 → 100 ms に
    最適化(線形→sRGB 逆曲線・L* 用 cbrt の前計算表への置換。L* 前計算に伴い
    grid/tile のゴールデンハッシュを更新)
  - M6 リグレッション(headless Chrome): スライダー追従 828 → 469 ms(改善)、
    タイル追加/削除の差分再マッチ 258/282 → 177/149 ms(改善)

### M8: 仕上げ

- 内容: 色補正強度・重複制御の設定 UI、JPEG 出力オプション、a11y(進捗バーの読み上げ)、コード整理、ドキュメント更新。
- 完了条件: 基本設計書の全画面・全機能が仕様どおりに動作し、既知の不具合がない。
- 実施結果(2026-10-19):
  - 色補正強度スライダー(`color_correct`、0〜1.0 Step 0.05、既定 0.85)と
    重複制御スライダー(`duplicate_de`、0.5〜8.0 Step 0.5、既定 2.0)を S2 に追加。
    いずれもメイン画像ブレンドと同じくドラッグ確定(マウスを離した)時に
    設定更新 → フル再生成する(基本設計書 3.3 の再処理ルールに追記済み)。
    UI で露出する重複制御は距離閾値(`duplicate_de`)のみとし、detail 差の閾値
    (`duplicate_detail`)はコア既定値(4.0)を維持する(`setConfig` で変更可能)
  - 保存形式の選択(PNG 既定 / JPEG 品質 92)を S2 ツールバーに追加。
    ファイル名の拡張子は形式に追従(`.png` / `.jpg`)。出力はピクセルからの
    再エンコードのためメタデータの継承はなし(プライバシー保証は不変)
  - a11y: 進捗バーにアクセシブルネーム(`aria-label`)を付与し、フェーズ表示を
    `role="status"` で読み上げ対象にした(`role="progressbar"` + `aria-valuenow`
    と開閉ボタンの `aria-expanded` は M5 実装済み)
  - コード整理: main.ts の「設定更新 → フル再生成」を共通ヘルパー
    (`updateConfig` / `regenerateFull`)へ集約(ブレンド・色補正・重複制御で共用)
  - 検査: cargo fmt --check / clippy(-D warnings)/ test(112 ケース合格)、
    tsc --noEmit、ESLint、Vitest(94 ケース合格)、vite build すべて合格
  - 既知の不具合: なし(WASM ロード失敗環境のモックフォールバックは仕様どおり)

## 5. 1 ループの進め方(テンプレート)

各マイルストーン内の作業は次のサイクルで回す。

```
① コア: 関数とテストを実装(cargo test で緑)
② バインディング: wasm-bindgen 経由で輸出(d.ts が自動生成)
③ Web: bridge.ts 経由で UI に結線(モックから差し替え)
④ 計測: デバッグオーバーレイ/ベンチで所要時間を記録
⑤ 調整: 閾値(重み・バッチサイズ等)を実測値で見直し、詳細設計書の表を更新
⑥ リリース: マージ → デモ可能な状態を残す
```

- 閾値を変えたら必ず [詳細設計書のパラメータ表](../03_detailed_design.md#5-パラメータ閾値一覧) を更新する(設計と実装の不一致を防ぐ)。
- 各マイルストーン完了時にデモ用スクリーンショットと計測値を `docs/` 下の記録(またはコミットメッセージ)に残す。

## 6. ブランチ運び

- `main` は常にデモ可能。作業は短期ブランチ(1 マイルストーンを複数 PR に分割してよい)。
- コア変更 PR には「計測値の前後」を必ず添付する。
- Android 着手(M4 以降)後は、コア API・ホストバンドルの変更を Web/Android 両方のブランチで取り込む調整が発生するため、コアの API 変更 PR は独立させ、両者の追従を小さく保つ。

## 7. リスクと打ち手

| リスク | 打ち手 |
|---|---|
| WASM と JS の往復コピーで思ったより遅い | バッファ転送回数を最小化(API 設計済み)。計測して Worker + OffscreenCanvas への移行を判断(M5 以降) |
| 低スペック端末でプレビュー描画が追いつかない | 部分描画の間引き(2 バッチに 1 回)、プレビュー用の解像度分離 |
| タイル枚数が想定より多い(数千〜) | k-d 木(M7)、メモリガードの自動縮小 |
| コア API が Android で使いにくい | M4 の API 凍結前に関係者レビュー。Android 着手時のフィードバックは [06](./06_android_implementation_guide.md) の手順で反映 |

## 8. Android への引き継ぎタイミング

- M4(API 凍結)を過ぎたら [06_android_implementation_guide.md](./06_android_implementation_guide.md) に従って Android 側の骨格を着手できる。
- Web は M5〜M8 の間もコアの改善ループを続け、Android 側で見つかったインターフェース課題を随時吸収する。
