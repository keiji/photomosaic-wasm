# ハンドオフ資料 3: WASM 実装言語の選定(Go / Rust)

| 項目 | 内容 |
|---|---|
| 性格 | 共通コアを Go と Rust のどちらで実装すべきかの検討資料 |
| 結論 | **Rust を推奨**(決め手: バイナリサイズ、メモリ制御、Android との同一ソース再利用) |

## 1. 前提条件(本プロジェクトの制約)

1. コアは WASM としてビルドし、Web と Android の両方で**同じ .wasm を実行**する(Android は JavaScript エンジン(WebView 内蔵の V8)をホストとする。JNI によるネイティブ実行はセキュリティ方針として採用しない)。
2. 完全オフライン・モバイル動作のため、バイナリサイズとメモリ使用量が小さいほど良い。
3. 大きな画像バッファ(数十 MB 級)を長時間保持して計算する。
4. UI の応答性を保つため、バッチ処理単位で進捗をコールバックする。
5. 画像デコードはプラットフォーム側が担当するため、コアは純粋計算(ピクセル配列 → ピクセル配列)。

## 2. 比較表

| 観点 | Rust | Go(標準 GOOS=js) | Go(TinyGo) |
|---|---|---|---|
| バイナリサイズ | ◎ 100〜400 KB(LTO+opt-level=z) | △ 1.5〜2.5 MB(GC・ランタイム込み) | ○ 数百 KB(ただし制限あり) |
| 実行速度 | ◎ GC なし・予測可能 | ○ GC の影響で変動 | ○ 一部最適化が弱い |
| メモリ制御 | ◎ アリーナ的で安定。大量バッファに強い | △ GC ヒープが膨らみやすい | △ 同左(+機能制限) |
| JS バインディング | ◎ wasm-bindgen / wasm-pack が事実上標準。型定義・テスト・npm 公開まで一式 | △ wasm_exec.js によるランタイム公開。型定義は手書き | △ 同左(+制限) |
| 計算系エコシステム | ◎ ndarray ほか数値計算資産が多い | ○ 標準で足りる範囲は十分 | ○ |
| Android での再利用(同一 .wasm) | ◎ Web 産物(グルーシップ + d.ts)がそのまま WebView ホストで使える。バッファ受渡しの型付き API も資産になる | ○ wasm_exec.js を WebView で動かすことで可能(ランタイム込みでサイズ大) | △ 同左(+機能制限) |
| UI フリーズ耐性 | ◎ バッチ境界での制御返しが設計通りに書ける | ○ GC 停止が体感を乱すことがある | ○ |
| 学習コスト | △ 所有権・FFI の習熟が必要 | ◎ 学習・書き味が軽い | ◎ |
| ビルド・CI | ○ ターゲット追加(1 行)+ wasm-pack | ◎ 標準ツールのみ | ○ TinyGo インストールが増える |
| 長期保守リスク | 小(エコシステムが活発、wasm が一次ターゲット) | 中(GOOS=js の改善ペースは穏当。wasip1 への移行動向に注意) | 中(TinyGo 自体の対応状況に依存) |

## 3. 考察

### 3.1 決め手になった 3 点

1. **メモリと GC**
   フォトモザイク処理は「大きなバッファを確保し、長い計算の中で埋めていく」作業で、ヒープの揺らぎが性能と UI の滑らかさに直結する。GC を持たない Rust は、確保サイズとライフタイムを設計書どおりに固定でき、WASM リニアメモリの見積もりが立てやすい。

2. **Android での同一成果物再利用**
   Android は Web と同じ .wasm を JavaScript エンジン(WebView 内蔵の V8)ホスト上で実行する方針(セキュリティ方針により JNI ネイティブ実装は不採用)。Rust は wasm-pack が生成するグルーシップと型定義(d.ts)がそのまま Android ホストでも資産となり、実装ノウハウも豊富。Go の場合も実行自体は可能だが、ランタイム込みの大きなバイナリを端末で動かす点で不利となる。

3. **バインディングと開発体験**
   wasm-bindgen は「Rust 関数 → 型付き JS API + TypeScript 型定義 + テスト基盤」まで自動生成する。本プロジェクトのように進捗コールバック・バッファ転送・設定 JSON といったインターフェースを Web と Android で共通化するには、生成物の型がそのままドキュメントになる Rust 側が有利。

### 3.2 Go が有利な場合(逆転条件)

- チームが Go に精通しており Rust の学習コストを許容できない場合
- コアの計算が想定より軽く、GC・バイナリサイズの不利が問題にならない場合
- 将来コアをサーバー側(CLI・バッチ)でも再利用し、Go の運用資産に載せたい場合

この場合もまず TinyGo を含めてサイズ・速度を実測した上で再判定する。判定材料は [性能計測設計](./05_performance_measurement.md) で整える。

### 3.3 リスクと緩和(Rust 採用時)

| リスク | 緩和策 |
|---|---|
| 学習コスト | コアのモジュールを小さく保ち、FFI(unsafe)を core-wasm の薄い層に閉じ込める |
| wasm-bindgen のバージョン追随 | バージョンを固定し、M1 で動作確認済みの組合せを CI で維持 |
| 数値の決定性(Web/Android 差) | f32/f64 の混在禁止、演算順序固定をコーディング規約化し、ゴールデン画像テストで担保 |

## 4. 結論

| 項目 | 判定 |
|---|---|
| 採用言語 | **Rust**(単一ターゲット wasm32-unknown-unknown。Android は JavaScript エンジン ホストで同一 .wasm を実行) |
| 条件付き再検討ゲート | M1(WASM 骨格動作)完了時点で、サイズ・速度・実装効率を実測し再確認する |
| 記録 | 再検討結果・実測値は本書に追記して履歴を残す |
