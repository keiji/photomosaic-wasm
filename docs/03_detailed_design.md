### 1.2 レイヤーと依存の方向

```
[Web UI (TS)] ────────────► [ホスト層: ページの JS] ──────────────┐
                                                                  ├──► [core (Rust) を WASM として実行]
[Android UI (Kotlin)] ──► [ホスト層: JS サンドボックス(MessagePort / evaluate)] ─┘
```

- `core` はプラットフォーム非依存(標準ライブラリ + `no_std` 相当の算術のみ)。画像デコード・エンコード・ファイル I/O を含まない。
- Android は JavaScript エンジン(androidx.javascriptengine: `JavaScriptSandbox`)をホストに、Web と同一の .wasm を実行する。ホストとの双方向通信は MessagePort API を第一選択とし、非対応時は named data + evaluate、さらに非対応なら Base64 evaluate へ段階的にフォールバックする。JNI によるネイティブコードの実装は行わない(セキュリティ方針)。
- UI 層はビジネスロジックを持たず、状態管理(store / ViewModel)を経由してコアを呼び出す。
- ホスト層(Web のグルーシップ、Android の JavaScript エンジン ホスト)は薄く保ち、メモリ受け渡しとコールバック変換のみを担う。

## 2. コア API 仕様(言語中立的な論理 API)

バインディングごとの具体的実装(Web の wasm-bindgen / Android の JavaScript エンジン ホスト)はここから機械的に導出できるものとする。

| 関数 | 入力 | 出力 | 説明 |
|---|---|---|---|
| `setMainImage(rgba, w, h)` | RGBA ピクセル・寸法 | `GridInfo` | メイン画像を設定しグリッド・ブロック特徴量を計算。全体ブロック数を返す |
| `setBlockSize(px)` | px | `GridInfo` | ブロックサイズ変更(グリッド再計算・全ブロック再マッチ要求) |
| `addTile(id, featureThumb, composeThumb, w, h)` | タイル 1 枚分の 2 種サムネイル | `TileInfo` | 特徴量用サムネイル(32×32・ボックスフィルタ縮小済み)と合成用サムネイル(長辺 64 上限)をホストが生成して渡す。コアは特徴量算出・プール登録を行う |
| `removeTile(id)` | タイル ID | `void` | プールから削除。割当中ブロックは未確定へ戻す(次の差分再マッチ対象) |
| `beginRun() / stepRun(nowMs)` | 開始・1 バッチ進行 | `void` / `StepOutput` | 生成(P3+P4)を行バッチ単位で駆動する主経路(M5)。`stepRun` はバッチごとに進捗イベント・部分結果・完了フラグを返し、ホストはバッチ境界で JS/サンドボックスへ制御を返す(8.1) |
| `run()` | - | `void` | 同期で完走する一括実行(内部で `beginRun` + `stepRun` を完走させる便利経路。検証・ベンチ・サンドボックス内の駆動に使用) |
| `rematch()` | - | `void` | 差分再マッチ(M6)。未確定ブロックのマッチ・差し替え評価(4.4)を行い、再マッチした行のみ再合成する |
| `cancel()` | - | `void` | 実行中処理をバッチ境界でキャンセル(現時点までの合成結果と確定済み割当は保持。7.5) |
| `onProgress(cb)` | コールバック | `void` | 進捗イベント受け取り登録 |
| `onResult(cb)` | コールバック | `void` | 行バッチ単位の部分結果(RGBA + 位置)受け取り登録 |
| `getBlockMeanColors()` | - | RGB 3 バイト×ブロック数 | ブロック平均色(グリッドプレビュー描画用。メイン画像未設定時は空) |
| `getTileCount() / getTilesMemoryBytes()` | - | u32 | タイルプールの枚数・合成用サムネイル合計バイト数(メモリガード監視値) |
| `clearTiles() / clearMainImage()` | - | `void` | プール・メイン画像状態の破棄(リセット操作。大容量バッファを開放) |
| `exportImage()` | - | RGBA バッファ | 完成画像(または現時点までの合成結果)を取得 |
| `getConfig() / setConfig(json)` | 設定 JSON | 設定 JSON | 閾値パラメータの参照・上書き(全フィールド必須。5 章の範囲外はエラー) |
| `getMetrics()` | - | JSON | 性能計測結果(詳細は[性能計測設計](./handoff/05_performance_measurement.md)) |
| `getVersion()` | - | string | コアのバージョン文字列。UI がコアと UI の不整合を検知するために表示する |

注意:
- `run()` は呼び出し元スレッドを長時間ブロックしない。どのホストでも処理をバッチ単位に区切って JS の制御に返す(後述 8 章)。Android では JavaScript エンジン サンドボックス(別プロセス)上でバッチが進行し、アプリの UI スレッドは塞がない。進捗・部分結果の通知が必要な経路では `beginRun()` / `stepRun()` を使用し、同期の `run()` は検証・一括実行の便利経路として使い分ける。
- **エラーの伝播**: コールバック登録(onError)は廃止し、エラーは各呼び出しの**例外**として返す(不正入力・範囲外設定・メモリガード超過・メイン画像未設定など。Web は JS `Error`、WASM バインディングは `Result::Err(JsValue)` を介して Error に変換)。バッチ駆動中のエラーも `step_run` の例外としてホストが受け取り、Android ホストはこれを MessagePort の `error` メッセージへ変換する(handoff/06 §3.3)。
- 画像バッファの受け渡しは RGBA(1 ピクセル 4 バイト)に統一する。色順変換・リサイズ済みのデータを受け取る。
- ピクセルバッファの正規形: バイト順は R→G→B→A、格納は行優先(上→下、左→右)、非プリマルチプライ、色空間は sRGB として扱う。
- プラットフォーム間のデコード・縮小の差(実装・色空間・リサンプラ)は入力ピクセルの差として現れることを許容する。プラットフォーム間の出力一致は保証しない(決定性は同一ホスト内での検証による。11 章参照)。

## 3. データ構造

```text
GridInfo {
  width: u32, height: u32      // メイン画像(解析用正規化後)サイズ
  block_size: u32              // 1 ブロックの辺長 px
  cols: u32, rows: u32         // ブロック数(最終列/行は半端ブロック含む)
  total_blocks: u32 = cols * rows
}

BlockFeature {
  index: u32                   // ブロック番号 = row * cols + col
  mean_lab: [f32; 3]           // CIELAB 平均 (L*, a*, b*)
  detail: f32                  // 輝度 L* の標準偏差(0..128)
  weight: f32                  // 半端ブロックはピクセル数で重み調整
}

TileFeature {
  id: u64                      // アプリ側が採番
  thumb_w: u32, thumb_h: u32   // 合成用サムネイル寸法
  mean_lab: [f32; 3]           // CIELAB 代表色(周囲重み付き平均。4.3)
  detail: f32                  // L* の標準偏差(サムネイル全体)
  usage: u32                   // 現在の使用回数(個別。P3 の使用ペナルティは重複グループの合計で評価。4.4)
}

MatchResult {
  block_index: u32
  tile_id: u64
}

ProgressEvent {
  phase_code: string          // フェーズの安定識別子(例: "main_analyze"。7.1 の対応表)
  phase_ratio: f32            // 0.0..1.0
  overall_ratio: f32          // 0.0..1.0 (全フェーズ通し)
  assigned_blocks: u32        // マッチ済みブロック数(match中のみ有効)
  total_blocks: u32
}

ResultBatch {
  block_row_begin: u32, block_row_end: u32   // 完成した行範囲
  block_size: u32, width: u32                // 画素行への写像(row_begin * block_size)に使用
  rgba: buffer                               // width * (end - begin) * block_size * 4 バイトの合成済み RGBA
}
```

## 4. フォトモザイク処理の具体的な流れ

### 4.1 フェーズ一覧

| フェーズID | 名称 | 内容 | 主な実行者 |
|---|---|---|---|
| P0 | LOAD_MAIN | メイン画像のデコード・EXIF 反映・正規化縮小 | UI 層 |
| P1 | MAIN_ANALYZE | グリッド計算、ブロック特徴量算出 | コア |
| P2 | TILE_ANALYZE | タイルのデコード(UI 層)とサムネイル化・特徴量算出(コア) | 両層 |
| P3 | MATCH | 各ブロックへのタイル割り当て | コア |
| P4 | COMPOSE | タイルの描画・色補正による最終画像生成 | コア |
| P5 | EXPORT | エンコード・保存 | UI 層 |

```
P0 LOAD_MAIN ─► P1 MAIN_ANALYZE ─► (P2 TILE_ANALYZE) ─► P3 MATCH ─► P4 COMPOSE ─► P5 EXPORT
      UI層            コア                  繰返し可能        コア         コア         UI層
```

### 4.2 P1 メイン画像解析

1. グリッド計算: `cols = ceil(w / block_size)`, `rows = ceil(h / block_size)`。右端・下端は半端サイズのブロックになり得る(クリップ描画)。
2. 各ブロックについて:
   - sRGB → 線形 RGB 変換後に画素平均を算出(平均はリニアライトで取ることで自然な混色になる)。
   - 線形平均を CIELAB (D65) へ変換し `mean_lab` とする。
   - ブロック内 L*(明度)の標準偏差を `detail` とする。
   - 半端ブロックは画素数を `weight` に記録(合成時の描画領域にも使用)。
3. `total_blocks` を確定させ、`GridInfo` を UI へ返す(進捗バーの分母)。

### 4.3 P2 タイル解析

1. (UI 層)タイルファイルをデコードし EXIF 回転を反映、アルファ付きの場合は白背景へ合成。
2. (UI 層)特徴量用サムネイル(32×32、ボックスフィルタ=面積平均)と合成用サムネイル(最大 64×64、アスペクト維持)へ縮小し、コアへ渡す。
3. (コア)`mean_lab`(代表色)と `detail` を算出し、タイルプールへ登録。
   - `mean_lab`: 線形 RGB での**周囲重み付き平均** → CIELAB(D65)。特徴量サムネイルの
     中央区画(各辺の中央 1/2、面積 25%)を重み 1、周囲(面積 75%)を重み
     `tile_border_weight`(既定 2.5。1.0 で従来の全体平均と一致)として平均する。
     構図が「中央に被写体・周囲に背景」の写真タイルで全体平均を取ると代表色が被写体色に
     引き摺られ、配置後のブロック境界(タイル同士が接する周囲領域)の色が合わず
     継ぎ目・粒状感(つぶつぶ)の原因になるため、境界に接する周囲を基準にする。
     P3 のマッチングと P4 の色補正(分母)はこの代表色を共用する
   - `detail`: L* の標準偏差はサムネイル全体で算出(ブロック側と同一手法)
4. 特徴量はブロックサイズに依存しないため、**ブロックサイズ変更時は P2 を再実行しない**(キャッシュ再利用)。

### 4.4 P3 マッチング

各ブロックに対し、タイルプールから距離最小のタイルを選ぶ。

**距離関数**

```text
D(block, tile) = w_c * ΔE76(block.mean_lab, tile.mean_lab)
               + w_d * |block.detail - tile.detail|
               + λ   * tile.usage                 // 使用回数ペナルティ
               + n_p * nearness(tile)             // 直上・直左との近さペナルティ
```

**手順**

1. ブロックを行バッチ(既定 8 行)単位で走査する。
2. 各ブロックで上記距離を全タイルへ評価し最小を選ぶ(タイル数が多い場合の高速化は 4.5)。
3. 選択タイルの `usage` を 1 加算。
4. 行バッチごとに `onProgress` と `onResult`(部分結果)を発火。
5. キャンセル要求があればそこで中断する。

**近さペナルティ(似たタイル同士の隊接配置の抑制)**

- 候補タイルと直上・直左タイルの代表色距離が `neighbor_de`(ΔE76 換算)以内のとき、
  近いほど大きいペナルティを加算する:
  ```text
  nearness = max(0, 1 - ΔE76(候補, 隣接) / neighbor_de)   // 直上・直左の最大値(0..1)
  ```
- 同一タイル/同一視の複製が隣接すると ΔE76 ≒ 0 で nearness = 1(最大ペナルティ)。
  `neighbor_de` を超えるとペナルティなし(0)。ソフトペナルティとし、配置の
  ハード禁止は行わない(類似タイルしか残っていない場合のデッドエンド防止)。
- 実質的な禁止に近づけるには `n_p`(neighbor_penalty)を 1.0 まで上げる。

**使用回数の制御**

- 使用ペナルティ λ により、使われたタイルは徐々に選ばれにくくなり、タイル群が均等に散らばる。
- 全タイルの `usage` が上限 cap に達した場合は usage を一括リセットして継続(スタック防止)。
- ΔE76 < 2.0(視覚上ほぼ同一)の候補が複数ある場合は、`detail` が大きい方(情報量が多い方)を優先する。

**重複グループ(類似タイルの同一視)**

- 代表色の距離が `duplicate_de` 以下かつ `detail` 差が `duplicate_detail` 以下のタイル同士は
  「重複グループ」にまとめて同一視する。同一写真の複製・至近バーストが個別の `usage` で
  選ばれ続け、見た目上同じ写真が並んで使われるのを防ぐための規定。
- グループは代表(= グループ内最小 ID)基準で ID 昇順に決定的に構築する(遅延構築。
  タイルの追加・削除と閾値変更で無効化し、マッチング開始時に再構築)。
  A≈B・B≈C だが A≉C の連鎖は同一視しない(過マージ防止)。
- 使用ペナルティの `usage` は**グループ合計の使用回数**、usage cap の一括リセット判定は
  **全グループの合計基準**で評価する(同一視された複製でペナルティ・cap を回避できなくする)。
  隣接配置の抑制は重複グループではなく近さペナルティ(ペア距離を直接評価)で行う。
- 重複がなければ(すべて単独グループ)全判定がタイル単位の従来動作と一致する。
- グループ構築の所要時間は k-d 木と同じ `p2_index_build` 計測点に累積する。

**差分再マッチ(タイル追加・削除時)**

- **未確定ブロック** = マッチ結果を持たないブロック(初回生成前、ブロックサイズ変更後、タイル 0 枚だった期間の全ブロック)。
- タイル追加時: 追加タイルを P2 で解析した後、未確定ブロックを優先的にマッチする。全ブロック確定済みの場合は差し替え評価のみ行う。
  - 差し替え基準: 追加タイルを含む距離再計算で、現割当より `improve_margin`(ΔE 換算)以上良い候補がある場合に差し替える(使用回数・隣接ペナルティは再評価する)。
- タイル削除時: 削除タイルが割り当てられていたブロックのみ、現プールで再マッチする。
- 使用回数 `usage` は再マッチ後に現割当表から再集計する(ペナルティの連続性を保つ)。
- 差分再マッチも P3 として進捗・部分結果を発火する(`assigned_blocks` は全体ブロック数に対して計上)。

### 4.5 マッチングの高速化

| 条件 | 方式 |
|---|---|
| タイル数 ≤ 2,000 | 総当たり(3 次元 LAB + 詳細差)。SIMD 演算で十分高速 |
| タイル数 > 2,000 | 特徴ベクトル (L*, a*, b*, detail) の k-d 木で近傍探索。使用ペナルティは候補取得後の再評価で反映(k=4 次元、近傍候補上位 32 件を再評価) |

### 4.6 P4 合成

1. 出力バッファ(正規化後メイン画像と同寸法の RGBA)を確保。
2. 各ブロックへ、選択タイルの合成用サムネイルをブロック矩形にスケーリング描画(バイリニア)。
3. **色補正**: タイルのトーンをブロックのトーンへ寄せて、全体像の視認性を高める。
   ```text
   線形RGB空間で: out = tile_px * ( (1 - α) + α * block_mean / tile_mean )   (チャンネル毎)
   ```
   - `α`: 色補正強度(既定 0.85)。0 で補正なし(タイル原色のパッチワーク)、1 で完全なトーン一致。
   - `tile_mean` はタイルの周囲重み付き代表色(4.3 の `mean_lab`)。α=1 で出力の
     周囲重み付き平均がブロック平均と一致し、タイルの周囲(= ブロック境界に接する領域)が
     ブロック色へ強く寄る。背景(周囲)を目立たなくして平滑領域の継ぎ目・粒状感
     (つぶつぶ)を抑制する趣旨で、代表色の周囲重み付き平均化(4.3)と合わせて
     既定を 0.7 → 0.85 とした
   - ゼロ除算ガード: `tile_mean < 1/255` のチャンネルは補正係数 1 とする。
4. **メイン画像ブレンド**: `main_blend > 0` のとき、色補正済みブロック画素の上に
   元のメイン画像を不透明度 main_blend で重ねる(既定 0.2、範囲 0〜0.8)。
   ```text
   sRGB 空間で: out = tile * (1 - main_blend) + main * main_blend   (チャンネル毎)
   ```
   - 0 でブレンドなし(純モザイク)。値が大きいほど元画像が強く現れ、タイルの模様は薄れる
   - メイン画像の受け渡し: 合成の呼び出し側(BatchRunState.step)がメイン画像を渡し、
     compose 内では追加のバッファを保持しない(メモリの増分なし)
   - 部分合成・差分再合成・エクスポートのすべてに同じブレンドが反映される
4. 半端ブロックはクリップ描画。
5. 部分描画要求(P3 の行バッチ完了ごと)でも同じ処理をその行範囲に限定して実行し、UI へ `ResultBatch` を返す。

### 4.7 P5 エクスポート

- コアは RGBA を返すのみ。エンコードはプラットフォーム標準機能(Web: `toBlob`、Android: `Bitmap.compress`)。
- 既定形式 PNG。JPEG 選択時の品質は 92。
- **メタデータ除去**: 出力画像には入力画像のメタデータ(EXIF の撮影位置・撮影日等)を引き継がない。ピクセルバッファからの再エンコードにより構造的に取り除かれることを保証し、テストで検証する(11 章)。

## 6. エッジケースの扱い

| ケース | 扱い |
|---|---|
| ブロック数が 1(画像 < block_size) | ブロックサイズを `min(短辺)` に自動調整して案内 |
| タイルプール空での run | 実行せず、グリッド + 平均色プレビューのみ。進捗バーは 0% |
| タイル 1 枚のみ | 全ブロック同一タイル+色補正で成立(ペナルティの影響なし) |
| 極端な縦長/横長 | cols/rows は独立計算なので問題なし。行バッチも行単位で成立 |
| アルファ付きメイン画像 | 白背景合成の上で不透明化(出力も不透明) |
| 超大量タイル(>10,000) | メモリガードでサムネイル解像度を自動縮小。k-d 木を使用 |

## 7. 進捗コールバック設計

### 7.1 フェーズと全体進捗の配分

`overall_ratio` はフェーズごとの固定配分で算出する。

| フェーズ | 配分(重み) | phase_ratio の意味 |
|---|---|---|
| P1 MAIN_ANALYZE | 10% | 処理済みブロック行の割合 |
| P2 TILE_ANALYZE | 20% | 処理済みタイル数 / 全タイル数 |
| P3 MATCH | 55% | マッチ済みブロック数 / total_blocks |
| P4 COMPOSE | 15% | 合成済み行バッチ / 全バッチ数 |

(同一フェーズの再実行時も同じ配分を用いる。例: ブロックサイズ変更時は P1 からやり直すが配分は同一)

**スキップされたフェーズの再配分**: 実行に含まれないフェーズがある場合(例: ブロックサイズ変更時の P2 スキップ)は、含まれるフェーズの配分をその総和で正規化する(P1+P3+P4 = 80% → 各 12.5% / 68.75% / 18.75%)。進捗バーが途中で停滞しないための規定。

**UI 文言とフェーズ ID の対応**(文言化は UI 側のリソースで行う。コアは `code` のみ通知):

| フェーズ ID | UI 文言(日本語の対応例) | 発行者 |
|---|---|---|
| P0 LOAD_MAIN | 画像を読み込み中… | ホスト/UI 層(コア進捗には含まれない) |
| P1 MAIN_ANALYZE | メイン画像を解析中… | コア |
| P2 TILE_ANALYZE | タイルを解析中… | コア |
| P3 MATCH | タイルをマッチング中… | コア |
| P4 COMPOSE | 合成中… | コア |
| P5 EXPORT | 保存中… | ホスト/UI 層(コア進捗には含まれない) |
| DONE | 合成終了 | UI 層(生成完了時。コアの `phase_code` ではない) |

### 7.2 イベント発火ルール

- 発火間隔は **16ms 以上** または **overall_ratio が 1% 以上変化** したとき。UI 更新負荷を抑えつつ追従性を確保する。
- `assigned_blocks / total_blocks` は P3 中は毎バッチ更新される(UI の横方向進捗バーの入力)。
- 付帯情報の通知は `phase_code` のみ(M5 で確定。当初検討した `params` 付きの付帯情報は、進捗の数値そのものが `assigned_blocks / total_blocks` として通知されるため廃止)。コアは文言を持たず、`phase_code` → 文言の変換は UI 側のリソースで行う(基本設計 5 章の国際化方針と整合)。

### 7.3 プラットフォームごとのコールバック実装

| プラットフォーム | 実装 |
|---|---|
| Web (WASM) | `wasm-bindgen` の `Closure<dyn FnMut(JsValue)>` を登録。コアはバッチ境界で `progress` JS 関数を呼ぶ |
| Android | ホスト JS から MessagePort へ進捗メッセージ(JSON)を送信 → Kotlin 側受信コールバック → `callbackFlow` → `StateFlow<ProgressEvent>` → Compose が収集 |

### 7.4 部分結果通知

- P3 の行バッチ完了ごとに `ResultBatch` を通知する(進捗バーとは別系統)。
- UI は受信した行範囲をプレビューへ即座に転写する。これにより「メイン画像がフォトモザイクへ置き換わっていく」演出を実現する。
- UI 側の描画コストが高い場合(低性能端末)は、2 バッチに 1 回の間引き描画に落としてよい(UI 側の裁量)。

### 7.5 キャンセルと要求の合流

- `cancel()` は次のバッチ境界で効果を発揮する(バッチ単位のアトミックな中断)。
- キャンセル後の状態: 既存のマッチ結果・合成結果は保持。追加の進捗イベントは発火しない。
- **要求の合流**: 実行中に設定変更(ブロックサイズ・タイル追加/削除)が発生した場合、現在の行バッチ完了後に処理を中断し、最新の状態で必要なフェーズから再開する。複数の変更が蓄積した場合は最新の状態のみで再開する(古い中間状態の再実行は行わない)。
- 用途: ブロックサイズ連続変更中の無駄な再計算の中止、画面離脱。

## 8. スレッド・非同期モデル

### 8.1 Web

- WASM コアの処理はメインスレッドでバッチ実行し、バッチごとに JS へ制御を返す(`requestAnimationFrame` 相当のタイミングで次バッチを再開)。
- これにより進捗表示・部分描画が UI をブロックせずに行われ、かつ Worker / SharedArrayBuffer / スレッド対応 WASM に必要な COOP/COEP ヘッダのような制約を避けられる。
- 計測の結果バッチあたりの処理時間が 8ms を超えるようであれば、Web Worker + `OffscreenCanvas` への移行を検討する(インターフェースは変更不要)。

### 8.2 Android

- コアは JavaScript エンジン サンドボックス(androidx.javascriptengine の `JavaScriptSandbox` / `JavaScriptIsolate`)内で実行する。サンドボックスはアプリとは別プロセスで動くため、処理中もアプリの UI スレッドは塞がない。
- Kotlin ↔ ホスト JS の双方向通信は **MessagePort API** を第一選択とする(Kotlin → JS: 制御メッセージ。JS → Kotlin: 進捗・結果メッセージ)。
- 起動時に `JavaScriptSandbox.isFeatureSupported` で WASM / MessagePort / named data / Promise / `EVALUATE_WITHOUT_TRANSACTION_LIMIT` / isolate max heap を確認し、利用可能な組み合わせでトランスポートを選ぶ。
- MessagePort 経路では、Kotlin → JS の大容量データ(RGBA バイト列)は named data が使える場合は named data 提供 API で渡し、メッセージは JSON 文字列で参照(dataRef)のみを持つ。named data が無い場合は `inputBegin` の後に ArrayBuffer を MessagePort で送る。JS → Kotlin には named data の consume API が無いため、部分結果・完成画像は JSON メッセージの直後に 512 KiB 以下の ArrayBuffer チャンクとして送る。AndroidX JavaScriptEngine の ArrayBuffer は Binder のサイズ上限を超えられないため、48 MB の完成画像を 1 メッセージで送ることはできない。
- MessagePort 非対応時は named data + evaluate 経路を使う。入力は named data、出力は `evaluateJavaScriptAsync("__pmDrain()")` のポーリングで受け、バイナリは 512 KiB 単位の Base64 チャンクにする。
- named data 非対応時は Base64 evaluate 経路を使う。入力は `inputBegin` / `inputChunk` でチャンク転送し、出力は named data + evaluate 経路と同じ outbox / Base64 チャンクを使う。
- 画像のデコード・縮小・PNG エンコードは Kotlin 側(プラットフォーム API)が担当する。サンドボックスには DOM/Canvas がないため、内部はピクセル配列の計算に専念する。
- バッチ駆動はホスト JS 内で `begin_run` / `step_run` を呼び、サンドボックスに `setTimeout` が無いため `stepDone` → `step` の往復でバッチ境界を作る。境界で `cancel`・設定変更を受け付ける。
- タイル登録は `addTiles` control で一括送信する。バイナリはタイルごとの named data / 入力バッファ参照で渡し、ホスト JS が `wasm_bindgen.add_tile` を順に呼ぶ。応答は成功分の `tiles` と失敗理由の `errors` を分けて返し、Kotlin 側は部分成功を UI に反映する。
- キャンセルはコルーチンキャンセルに連動させ、選択中のトランスポート経由でホストの `cancel()` を呼ぶ。コアの `cancel()` は実行状態を破棄し、確定済みの合成結果を保持する。isolate は画面破棄時に close してリソースを解放する。

## 9. メモリ設計

| 項目 | 目安 | 手段 |
|---|---|---|
| メイン画像(解析・出力用) | 4096×3072 RGBA ≈ 50 MB(正規化後) | 正規化縮小。解析・合成・出力はすべてこの解像度 |
| タイル特徴 | 32×32 Lab ≈ 1 KB/枚 | 数万枚に耐える |
| タイル合成サムネイル | 64×64 RGBA ≈ 16 KB/枚 × memory_guard(3,000 枚で約 48 MB) | 上限超過で解像度半減 |
| WASM ヒープ | 初期 256 MB 相当 | 伸長は wasm-bindgen 既定に任せ、失敗時はエラーとして UI へ通知。Android ではサンドボックス(isolate)のメモリ上限(端末依存)があるため、実機での上限確認を品質確認に含める |
| Android のバイナリ受信バッファ | 完成 RGBA と同サイズ | 応答の `length` を先に受け取り、チャンク到着時に最終サイズの `ByteArray` を一度だけ確保する。MessagePort / evaluate の双方で 512 KiB チャンクを同じバッファへ書き込み、`ByteArrayOutputStream` の伸長と `toByteArray()` の複製による Java ヒープの倍化を避ける |

## 10. 性能目標と計測

フェーズごとの所要時間はコア内部で常時計測され `getMetrics()` で取得できる。Android では Kotlin の `CoreEngine.getMetrics()` と host.js の `getMetrics` control を経由してメトリクス JSON を取得する。Web は生成完了後に直近 run のサマリをオーバーレイ表示し、Android も合成終了後にサマリを表示する。どちらも表示の右側にコピーアイコンを置き、メトリクス JSON をクリップボードへコピーできる。表示は × ボタンで閉じるまで維持し、次の計測更新で再表示する。
目標値・計測方法の詳細は [性能計測設計](./handoff/05_performance_measurement.md) を参照。

参考目標(ミッドレンジデスクトップ、メイン 12MP / タイル 300 枚 / ブロック 24px):

| フェーズ | 目標 |
|---|---|
| P1 MAIN_ANALYZE | 300 ms 以内 |
| P2 TILE_ANALYZE(300 枚) | 200 ms 以内(デコード除く) |
| P3 MATCH | 1.0 秒以内 |
| P4 COMPOSE | 1.0 秒以内 |
| 合計(初回) | 3 秒以内 |
| ブロックサイズ変更時の再生成 | 1.5 秒以内(P2 スキップの効果) |

## 11. テスト設計(概要)

| レベル | 内容 |
|---|---|
| コア単体 | 色変換の既知値検証(sRGB↔Lab 往復誤差 < 0.1)、グリッド計算の端数、距離関数の性質(使用ペナルティで順位が変わること等) |
