# JS / WASM メモリフットプリント比較

## 1. 目的

WASM 版(`index.html`)と純 TypeScript 版(`index_js.html`)のメモリフットプリントを、
同一の画像・タイル・設定で比較する。

速度比較は [04_performance_comparison.md](./04_performance_comparison.md) を参照。

## 2. 計測方法

- Chromium の `performance.measureUserAgentSpecificMemory()` を使用する。
- 同 API は cross-origin isolation(COOP/COEP)が必要なため、
  `tools/memory-benchmark.mjs` が `web/dist` を COOP/COEP 付きでローカル配信する。
- ヘッドレス Chrome を起動し、WASM 版と JS 版で同じ画像・タイルを読み込み、
  生成完了後のメモリを計測する。
- タイル読み込み後(生成前)と生成完了後の 2 点で、それぞれ 3 回計測した中央値を採用する。
- 値はページの JS ヒープ、Worker、DOM、Canvas、Shared の合計である。
  GPU・コンポジタ・ブラウザプロセス全体の RSS は含まない。

## 3. 計測条件

- 日付: 2026-10-20
- ブラウザ: Chrome 155.0.8059.84(ヘッドレス)
- OS / CPU: Linux x86_64 / AMD Ryzen 7 PRO 6850U
- 配信: `web/dist` をローカル HTTP サーバーで配信(COOP/COEP 有効)
- メイン画像: 1920×1080
- タイル: 1,000 枚(2000×1500 の元画像を長辺 64px へ縮小)
- ブロックサイズ: 24 px
- 設定: 既定値(`row_batch = 8`)
- 出力 Canvas: 1920×1080

## 4. 計測結果

### 4.1 ページ全体

| 時点             |       JS |     WASM |
| ---------------- | -------: | -------: |
| タイル読み込み後 | 40.59 MB | 49.86 MB |
| 生成完了後(保持) | 40.62 MB | 49.84 MB |

生成完了後の WASM は JS より約 **9.22 MB(約 22.7%)大きい**。
タイル読み込み後と生成完了後の差は小さく、生成時点で確保済みのバッファが
大部分を占めている。

生値(bytes):

| 時点             |         JS |       WASM |
| ---------------- | ---------: | ---------: |
| タイル読み込み後 | 40,587,328 | 49,859,958 |
| 生成完了後(保持) | 40,619,226 | 49,843,478 |

### 4.2 生成完了後の内訳

| 項目              |       JS |     WASM |
| ----------------- | -------: | -------: |
| Worker JavaScript | 30.46 MB | 39.73 MB |
| Window JavaScript |  0.61 MB |  0.61 MB |
| Canvas            |  8.29 MB |  8.29 MB |
| DOM               |  0.60 MB |  0.60 MB |
| Shared            |  0.65 MB |  0.61 MB |
| **合計**          | 40.62 MB | 49.84 MB |

WASM の Worker JavaScript には WASM の linear memory が含まれる。
差分の大部分は Worker 側で、WASM の Worker は JS の Worker より約
**9.26 MB(約 30.4%)大きい**。

## 5. 解釈

- WASM は linear memory が生成後に縮まないため、タイル・メイン画像・合成結果を
  保持したままになりやすい。
- JS は一時バッファが GC で回収されやすく、このワークロードでは保持量が小さくなった。
- Window JavaScript、Canvas、DOM は両実装でほぼ同じだった。
- 速度とメモリはトレードオフになる。今回の条件では WASM の方が高速だが、
  保持メモリは大きい。

## 6. 注意点

- `performance.measureUserAgentSpecificMemory()` は Chromium 系かつ
  cross-origin isolation が必要である。GitHub Pages は COOP/COEP ヘッダを返さないため、
  公開版ではそのまま使えない。
- CDP の `Runtime.getHeapUsage` だけでは WASM の linear memory が十分に含まれず、
  JS 側も GC 後の backing storage が過大に見えることがある。
  本比較では UAM の値を採用した。
- 値はページ内の JS / Worker / DOM / Canvas の概算であり、GPU・コンポジタ・
  ブラウザプロセス全体のメモリではない。
- 1 データセット・1 回の計測である。結論を一般化するには、画像サイズ・タイル数・
  ブロックサイズを変えた複数回の計測が必要である。
- Service Worker のキャッシュが残ると計測を誤るため、スクリプトは新しい
  ブラウザプロファイルを使い、HTTP キャッシュを無効化する。

## 7. 再計測方法

```bash
cd web
npm run build
cd ..

node tools/memory-benchmark.mjs \
  --main /path/to/main.png \
  --tiles /path/to/tiles \
  --tile-limit 1000
```

主なオプション:

| オプション       | 内容                                     |
| ---------------- | ---------------------------------------- |
| `--main`         | メイン画像のパス(必須)                   |
| `--tiles`        | タイル画像のディレクトリ(必須)           |
| `--tile-pattern` | タイルファイル名の接頭辞(既定: `tile`)   |
| `--tile-limit`   | 使用するタイル数の上限(既定: 全件)       |
| `--samples`      | UAM の計測回数(既定: 3)                  |
| `--out`          | JSON 結果の出力先                        |
| `--chrome`       | Chrome / Chromium のパス(既定: 自動検出) |

Chrome が見つからない場合は `CHROME_BIN` 環境変数で指定する。
スクリプトはローカルサーバーとヘッドレス Chrome を自動で起動・終了する。

## 8. WASM の性能的優位性と採用判断

### 8.1 ベンチマークから言えること

速度は 1920×1080・タイル 300 枚・`row_batch = 8`、メモリはタイル 1,000 枚の条件である。

| 観点                    | 結果                        | 解釈                                  |
| ----------------------- | --------------------------- | ------------------------------------- |
| 生成時間                | JS 336 ms → WASM 237 ms     | 約 29% 短縮(約 1.42 倍速)             |
| `row_batch = 32` の合計 | JS 330 ms → WASM 317 ms     | 約 4% 差まで縮む                      |
| `row_batch = 32` の run | JS 268 ms → WASM 275 ms     | WASM がわずかに遅い                   |
| `opt-level = "z"`       | WASM 345 ms                 | JS より遅い。最適化設定の影響が大きい |
| ページ全体メモリ        | JS 40.62 MB → WASM 49.84 MB | WASM が +9.22 MB(約 +22.7%)           |
| Worker メモリ           | JS 30.46 MB → WASM 39.73 MB | WASM が +9.26 MB(約 +30.4%)           |

- 計算が支配的で、バッチ待ちが小さい場合は WASM が有効である。
- `requestAnimationFrame` 待ち、Worker RPC、バッチ境界、データ転送が入ると差は急速に縮む。
- WASM の linear memory は生成後に縮みにくいため、保持メモリは増えやすい。
- JS の JIT も数値計算に十分強く、「WASM でなければ実現できない」という差ではない。
- 今回の計測は生成時間のみで、WASM のコンパイル・インスタンス化を含む起動時間は未計測である。

一般的な数値計算カーネルでは、WASM の速度優位は 1〜2 倍程度の範囲に収まることが多く、
ワークロード・最適化・JS-WASM 境界のコスト次第で逆転する。10 倍速くなるという期待は現実的ではない。

### 8.2 WASM が向く条件

- 既存の Rust / C / C++ 資産をそのまま使える。
- 画像・音声・圧縮・暗号・シミュレーションなど、計算支配の処理である。
- 型付き配列や大きなチャンクをまとめて渡せ、JS-WASM 境界の呼び出しが少ない。
- JS の JIT や GC の影響を抑え、ブラウザ間の性能差を小さくしたい。
- Web / Node / Android / デスクトップで同一コアを再利用したい。
- 外部コードをサンドボックス内で動かしたい。
- SIMD やスレッドを使った重い数値処理へ拡張する可能性がある。

一方、DOM・文字列・オブジェクト操作が中心、小さな処理を高頻度で呼ぶ、起動時間や
メモリ予算が厳しい、既に最適化された JS で十分速い場合は、JS を優先した方がよい。

### 8.3 採用判断チェックリスト

| チェック項目   | WASM 寄り                                    | JS 寄り                              |
| -------------- | -------------------------------------------- | ------------------------------------ |
| ホットスポット | 計算・画像処理・圧縮・暗号・シミュレーション | DOM・文字列・オブジェクト操作・I/O   |
| データ構造     | 連続した型付き配列、大きなチャンク           | 小さなオブジェクトを大量に扱う       |
| JS-WASM 境界   | 呼び出し回数が少なく、まとめて渡せる         | 高頻度の細かい呼び出し               |
| 性能の安定性   | ブラウザ差・GC 差を抑えたい                  | ピーク性能より開発速度を優先         |
| メモリ予算     | +20〜30% の余裕がある                        | メモリが厳しい、低スペック端末を重視 |
| 起動時間       | コンパイル・インスタンス化コストを許容       | 初回表示を最優先                     |
| 既存資産       | Rust / C / C++ の資産がある                  | 既に最適化された JS がある           |
| 再利用性       | Web / Android / Node で共通コアが必要        | Web だけで完結                       |
| セキュリティ   | 外部コードを隔離したい                       | 通常の JS で十分                     |

目安として、WASM 寄りの項目が 3〜4 個以上あれば検討し、5〜6 個以上なら採用候補、
1〜2 個なら JS 優先とする。

定量的な目安:

- 計算が全体時間の 50% 以上を占める。
- 数 MB 以上の型付き配列をコピーなしで渡せる。
- 想定高速化が 20〜30% 以上ある。
- WASM 化によるメモリ増が 20〜30% 以内に収まる。
- 低スペック端末での起動・コンパイル時間が許容範囲である。
- JS-WASM 境界のデータ転送コストが計算時間より小さい。

高速化が 10〜20% 程度で、メモリが +30% 増え、境界呼び出しが多い場合は、
WASM 化の複雑さに見合わないことが多い。

### 8.4 本アプリでの結論

本アプリは WASM 寄りの要素が多い。

- 画像処理・マッチング・合成は計算支配である。
- 型付き配列・Canvas・大量タイルを扱う。
- Web と Android で同一コアを再利用できる。
- 性能の安定性・サンドボックス性に価値がある。
- Rust コアという既存資産がある。

一方で、WASM が不利な要素もある。

- メモリ保持量が JS より約 23% 多い。
- タイル数・画像サイズが大きいと linear memory の high-water mark が増える。
- 起動・コンパイル時間は未計測である。
- `row_batch = 32` では速度差が約 4% まで縮む。
- JS 版の出来が良く、Web だけなら JS でも十分戦える。

したがって、現実的な方針は次のとおり。

- WASM を既定とする。ただし理由は「圧倒的に速い」ではなく、
  共通コア・計算性能・性能の安定性である。
- JS 版はフォールバックとして維持する。メモリが厳しい端末や WASM 非対応環境で有効。
- 中間バッファの解放・再利用、タイル特徴量の圧縮、コピー削減、タイル数上限など、
  メモリ最適化の余地を検討する。
- 起動時間と低スペック端末でのメモリを追加計測する。今回の計測だけでは、
  初回ロードを含む体感性能は判断できない。

## 9. まとめ

- 1920×1080、タイル 1,000 枚の条件では、生成完了後のページ全体は
  JS 40.62 MB、WASM 49.84 MB だった。
- WASM は JS より約 9.22 MB(約 22.7%)大きい。
- 差分の中心は Worker の保持メモリで、WASM の linear memory が縮まないことが主因と考えられる。
- WASM の速度優位は計算支配の処理で 1〜2 倍程度であり、条件依存である。
- WASM の採用理由は速度だけでなく、共通コア・性能の安定性・サンドボックス・再利用性にある。
- 本アプリは WASM 既定 + JS フォールバックが妥当である。
- メモリ上限が厳しい環境では、タイル数・画像サイズ・ブロックサイズを調整する必要がある。
